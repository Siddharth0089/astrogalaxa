# Decisions

- The visible product name is Astro Galexa. The existing native package identifiers and secure-storage keys remain unchanged to avoid breaking existing installations; final owned identifiers must be chosen before creating OAuth/Firebase clients or publishing. `MONGODB_DB_NAME` defaults to `astro_galexa` and explicitly selects the database, overriding the database portion of the URI.

- OTP challenges use a unique email index and conditional writes for cooldown, attempt reservation, and single-use consumption. Request caps include a Mongo-backed fixed-hour email counter and per-process IP limits; a distributed rate-limit store, sliding-window semantics, replica-set concurrency tests, and index migration checks remain required before deployment. The server does not trust proxy headers by default; configure trusted proxy addresses for the chosen hosting topology before production.
- User self-service account deletion uses a MongoDB transaction to remove the user, their sessions, OTP challenge, device tokens, astrologer subscriptions, Kundli, tarot readings, and owned chat threads and messages. Transactions require a replica set or sharded cluster; the current standalone Compose MongoDB does not support deletion. Astrologer/admin deletion requires a separate support process. In-flight writes, backups, future collections, retention and production operational deletion procedures still require review before launch.

- Native sessions are stored in Expo SecureStore; the browser preview keeps sessions in memory only. The client shares concurrent refresh requests and restores a session on launch. Refresh tokens rotate with a conditional update on a single session document, retaining prior hashes for reuse detection. Access tokens contain a session ID and protected requests check the active user and session in MongoDB, so logout and reuse revocation take effect on subsequent requests. Older access tokens without a session ID are rejected; clients must refresh or sign in again after this change. Integration tests cover basic OTP and refresh races, but production load, distributed behavior, and failures still need testing.

- Development place search uses Open-Meteo's geocoding API (GeoNames data) and returns its coordinates and IANA timezone. Review provider terms, attribution, quotas and commercial access before production; do not substitute fixed coordinates when lookup fails.

- Production startup is intentionally disabled while the app and backend lack required features and release verification. Socket connections are also rejected until authentication and thread authorization are implemented.

- The name-sign syllable table is a configurable editorial seed; a qualified Vedic astrologer must review it before launch.
- The displayed sun sign uses tropical date ranges and is explicitly labelled “by birth date”; the Kundli engine is sidereal (Lahiri).
- Birth time omitted uses local noon and returns `approximate`; ascendant and houses are intentionally omitted.
- Kundli calculations use Swiss Ephemeris with Lahiri sidereal mode and Moshier calculations. Swiss Ephemeris is AGPL/commercial dual-licensed: the owner must select an appropriate licence before launch. Independent reference-chart comparisons, native builds on deployment platforms, DST ambiguity UX, and astrologer review are required. Results are recomputed on each request for now so current Dasha periods cannot become stale; the stored record is not yet used as a cache.
- Credentials are intentionally absent. In development, `OTP_LOG_CODES=true` logs OTPs and delivery is mocked unless Resend is configured.
- Tarot uses a seeded Major Arcana deck and position-specific reflective prompts, for entertainment only. The seed command inserts missing cards and does not overwrite existing definitions. The current line art is illustrative and needs visual review against the supplied design.
- Daily horoscope fallback is fixed, per-sign seeded editorial content, not generated or personalized daily forecasts. Saved entries are keyed by sign and local date. Editorial review and a content-generation/update process are still required before launch.
